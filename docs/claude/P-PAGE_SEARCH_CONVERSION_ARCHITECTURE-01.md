**문서 상태:** ACTIVE / ARCHITECTURE 정본 — P페이지·P페이지 검색자산 작업 시 필독\
**프로젝트:** AI-POST\
**작성일:** 2026-10-03\
**적용 대상:** P페이지(`/p/[storeId]`) 및 향후 P페이지 검색 자산\
**개발 원칙:** One Axis · TRACE FIRST · FACT FIRST · 최소 구현 · 실증 후

## 1. 목적

P페이지는 단순한 업체 소개 홈페이지가 아니다.

> **P페이지는 `지역 + 하는 일(서비스)` 검색에서 검색엔진 상단노출을
> 목표로 하는 검색자산이며, 검색을 통해 들어온 사용자가 실제 업체정보를
> 확인하고 해당 업체에 직접 전화·문자·길찾기·문의하도록 연결하는
> 선택·전환 페이지다.**

P페이지의 우선순위는 다음 두 가지다.

1.  **1차 목적 --- 검색 상단노출**
2.  **2차 목적 --- 가입업체 직접 전환**

따라서 앞으로 P페이지에 추가하는 기능은 반드시 다음 질문으로 판단한다.

-   검색엔진이 업체·지역·서비스 관계를 더 명확하게 이해하는가?
-   실제 검색자가 이 업체가 무엇을 하는 곳인지 더 빨리 판단할 수 있는가?
-   전화·문자·길찾기·문의 등 실제 업체 전환에 도움이 되는가?

세 질문 중 어느 것에도 기여하지 않는 기능은 우선 개발 대상에서 제외한다.

## 1-A. 상위 설계 원칙 — 블로그 도구에서 업체 검색 기반으로

> **이 절이 AI-POST 상위 설계 원칙의 정본이다.** (구 `AI-POST_BUSINESS_SEARCH_FOUNDATION_PRINCIPLE-01` 은 독립 정본으로 두지 않는다.)

AI-POST의 출발점은 블로그 콘텐츠 생성이었지만, 장기 구조를 **블로그 글 생성 서비스 하나에 종속시키지 않는다.**

AI-POST가 구축하려는 기반은 **지역 사업자의 실제 FACT를 중심으로 한 검색·콘텐츠·전환 인프라**다.

``` text
업체의 실제 FACT 구축
        ↓
업체 / 지역 / 실제 제공 서비스의 관계 형성
        ↓
검색 목적에 맞는 여러 자산으로 전개
        ↓
P페이지 / pSEO / Blog / Shorts / FAQ / AI Discovery
        ↓
네이버·구글·향후 AI 검색 등 다양한 발견 경로
        ↓
업체 확인·비교·선택
        ↓
전화·문자·길찾기·문의
        ↓
가입업체의 상담·고객·매출 기회
```

### 1-A-1. 블로그는 전체 구조의 한 채널이다

Blog는 중요하지만 AI-POST 전체 시스템 그 자체가 아니다.

Blog는 사용자의 구체적인 질문·문제·정보 탐색에 답하고 전문성과 설명을 제공하는 콘텐츠 자산이다.

따라서 P페이지나 pSEO를 Blog 본문의 복사본으로 만들지 않는다.

### 1-A-2. 업체 FACT Core가 기초다

시스템의 중심은 생성된 문장이 아니라 **실제 업체 FACT**다.

FACT 후보는 다음과 같다.

- 업체명
- 지역/주소
- 실제 서비스 지역
- 실제 제공 서비스
- 영업시간/휴무
- 전화/연락 방법
- 실제 업체사진/작업사진
- 상담 방식
- 작업/진료/업무 방식
- 견적 또는 이용 방식
- 사후관리 방식
- 실제 차이와 선택 이유
- 관련 발행 콘텐츠

존재하지 않는 FACT를 검색노출을 위해 AI가 만들어서는 안 된다.

### 1-A-3. 하나의 FACT에서 여러 검색자산을 만든다

``` text
하나의 FACT Core
├─ P페이지
├─ pSEO
├─ Blog
├─ Shorts
├─ FAQ
└─ AI Discovery
```

데이터 원천을 채널마다 복제하지 않는다.

**같은 FACT를 사용하되 각 자산의 검색의도와 역할에 맞게 표현 방식을 분리한다.**

### 1-A-4. 각 자산의 역할을 혼합하지 않는다

- **P페이지:** 업체의 중심 검색·선택·전환 노드
- **pSEO:** 지역·서비스 등 구체적인 검색의도에서 업체를 발견시키는 검색 진입 자산
- **Blog:** 질문·문제·서비스에 대한 설명과 정보 콘텐츠
- **Shorts:** 문제 발견·관심 형성과 업체 발견의 입구
- **FAQ / AI Discovery:** 업체 FACT를 질문·답변 구조로 이해하고 가져갈 수 있도록 하는 확장 레이어

각 자산의 역할은 다르지만 원천 FACT는 가능한 한 공유한다.

### 1-A-5. 검색 상단노출은 구조적으로 만든다

검색용 단어를 억지로 반복하거나 지역명만 바꾼 페이지를 대량 생산하는 것을 기본 전략으로 삼지 않는다.

검색엔진이 다음 관계를 명확하게 이해할 수 있도록 한다.

``` text
이 업체는 누구인가
×
어디에 있는가
×
어디까지 서비스하는가
×
실제로 무엇을 하는가
×
어떻게 일하는가
×
왜 선택할 이유가 있는가
×
어떻게 직접 연락하는가
```

이 관계 자체가 AI-POST 검색 기반의 기초공사다.

### 1-A-6. 최종 목적은 가입업체의 사업 성과다

노출·색인·순위·방문수 자체를 최종 성공으로 정의하지 않는다.

``` text
검색될 이유
→ 발견될 기회
→ 읽고 확인할 이유
→ 선택할 이유
→ 직접 연락할 이유
→ 상담·고객·매출 기회
```

AI-POST는 이 연결 구조를 제공하고 측정하는 플랫폼 역할에 집중한다.

### 1-A-7. 개발 판단 기준

새로운 기능을 제안하거나 구현하기 전에 반드시 판단한다.

> **이 기능이 업체 FACT를 더 정확하게 구축하거나, 검색 발견 가능성을 높이거나, 사용자의 업체 선택 또는 직접 전환을 개선하는가?**

그렇지 않다면 현재 핵심 개발에서 제외한다.

**이 상위 원칙은 기존 P페이지의 `1차 목적 = 검색 상단노출`, `2차 목적 = 가입업체 직접 전환`, FACT 계약, 금지사항, 개발순서를 변경하지 않는다. 기존 구조를 해석하는 상위 기준이다.**

## 2. 핵심 흐름

``` text
[외부 검색엔진]
지역 + 하는 일(서비스)
        ↓
[검색 노출 자산]
업체/지역/서비스 관계를 명확하게 표현
        ↓
[업체 발견]
업체명 / 지역 / 대표 서비스 / 대표사진
        ↓
[업체 P페이지]
실제 업체 FACT 확인
        ↓
사진 / 실제 제공 서비스 / 영업정보 / 이용정보
업무방식 / 실제 선택 이유 / 관련 콘텐츠
        ↓
[직접 전환]
전화 / 문자 / 길찾기 / 문의
        ↓
[가입업체의 고객·상담·매출 기회]
```

**중요:** 사이트 내부 검색창 자체가 목적이 아니다.\
핵심은 검색엔진이 `지역 + 하는 일` 관계를 이해하고 P페이지 및 관련
검색자산을 검색 결과에 노출할 수 있도록 만드는 것이다.

## 3. P페이지 정보 구조

### A. 업체 식별 영역

검색자와 검색엔진이 즉시 업체를 식별할 수 있어야 한다.

-   업체명
-   지역
-   업종/분야
-   실제 하는 일 또는 대표 서비스
-   주소
-   연락처

### B. 즉시 행동 CTA

업체 확인 후 행동까지의 거리를 짧게 유지한다.

-   전화
-   문자
-   길찾기
-   향후 필요 시 직접 문의

**원칙:** AI-POST 운영자가 상담을 중간에서 받지 않는다. 사용자는
가입업체와 직접 연결된다.

### C. 업체사진

사진은 장식이 아니라 실제 업체를 판단하기 위한 FACT 자산이다.

기본 구조:

``` text
대표사진
↓
썸네일 최대 6장
↓
썸네일 클릭
↓
큰 사진 교체
```

원칙:

-   첫 번째 사진을 초기 대표사진으로 사용
-   최대 6장
-   PC/모바일 모두 과도한 화면 점유 금지
-   사진 때문에 영업정보·서비스·CTA가 지나치게 아래로 밀리지 않게 구성
-   공개 페이지에서 썸네일 선택은 화면 표시만 변경하며 DB의 대표사진을
    변경하지 않음
-   팝업·라이트박스·슬라이더·확대는 별도 필요성이 검증되기 전까지 기본
    기능에 포함하지 않음

### D. 실제 제공 서비스

P페이지 검색가치의 핵심 영역이다.

예:

``` text
인테리어
 ├ 주방 리모델링
 ├ 욕실 리모델링
 ├ 도배
 ├ 장판
 └ 타일 시공
```

단, **엔진 업종 분류나 발행 키워드를 실제 제공 서비스 FACT로 임의
전환하지 않는다.**

실제 제공 서비스는 업체가 실제로 제공한다고 확인된 FACT를 원천으로 해야
한다.

### E. 영업·이용 정보

검색자가 실제 이용 가능 여부를 판단할 수 있는 정보다.

-   영업시간
-   휴무
-   서비스 지역
-   방문/출장 여부
-   예약/상담 방식
-   오시는 길
-   주차
-   방문 또는 상담 전 준비사항

존재하는 FACT만 노출한다. 빈 항목을 채우기 위해 AI가 사실을 생성하지
않는다.

### F. 실제 업무방식

광고문구가 아니라 업체가 실제로 어떻게 일하는지를 보여준다.

예:

-   상담 방식
-   작업 진행 방식
-   현장 확인 여부
-   견적 방식
-   사후관리 방식

### G. 실제 선택 이유

`최고`, `1등`, `무조건 만족` 같은 광고문구를 만드는 영역이 아니다.

업체가 제공한 실제 사실에서만 선택 이유를 만든다.

``` text
실제 FACT
→ 검색자가 이해할 수 있는 표현
→ 선택 판단에 도움
```

AI가 업체의 경험·성과·효과·전문성을 임의 생성하지 않는다.

### H. 관련 콘텐츠

P페이지와 블로그를 동일 문서로 만들지 않는다.

P페이지는 업체·지역·서비스 탐색 및 전환 역할을 맡고, 블로그는
정보·설명·전문성·설득 역할을 맡는다.

필요한 경우 P페이지에서 실제 발행 콘텐츠로 연결한다.

## 4. 검색 구조

향후 P페이지 검색자산은 다음 관계를 중심으로 설계한다.

``` text
지역
 ×
업체
 ×
실제 제공 서비스
```

예:

``` text
덕소 + 인테리어
덕소 + 욕실 리모델링
남양주 + 주방 리모델링
```

단순히 지역명 또는 서비스명만 바꿔 동일한 본문을 대량 생성하지 않는다.

각 검색자산은 실제 업체 FACT와 검색의도가 존재해야 한다.

### 검색 구조의 역할

``` text
검색될 이유
→ 들어올 이유
→ 업체를 확인할 이유
→ 선택할 이유
→ 연락할 이유
```

검색 상단노출 자체가 최종 사업 목적은 아니다.

``` text
검색 노출
→ 방문
→ 전화/문자/길찾기/문의
→ 유효 상담
→ 가입업체의 매출 기회
```

까지 연결되는 구조를 목표로 한다.

## 5. 공통 FACT 계약

P페이지 때문에 별도의 업체 사실 복사본을 만들지 않는다.

원칙:

> **데이터는 하나, 노출 방식은 채널·검색엔진별로 분리한다.**

공통 FACT 후보:

-   업체명
-   주소
-   지역
-   연락처
-   운영시간
-   휴무
-   실제 제공 서비스
-   서비스 지역
-   상담/예약 방식
-   실제 업무방식
-   실제 차이/선택 이유
-   사진
-   FAQ
-   관련 발행 콘텐츠

P페이지·pSEO·Blog·Shorts·FAQ·향후 AI Discovery는 가능한 한 동일한 업체
FACT Core를 서로 다른 방식으로 읽는다.

## 6. 현재 데이터 경계

현재 구조에서 다음 개념을 혼합하지 않는다.

-   `departments` = 겸업/엔진 분야 분류
-   발행 `core_keyword/full_keyword` = 발행·검색 기록
-   엔진의 treatment/menu 데이터 = 콘텐츠 생성용 엔진 데이터
-   **업체 실제 제공 서비스 FACT = 별도 개념**

따라서 기존 값을 편의상 실제 서비스 FACT로 둔갑시키지 않는다.

신규 DDL은 실제 제공 서비스의 최소 저장계약이 확정되고 기존 구조로
해결할 수 없는 것이 확인된 뒤 별도 승인한다.

  플랫폼 중개 견적             제외          직접 전환 원칙과 불일치
  AI-POST가 상담 중개          제외          가입업체 직접 전환 원칙과 불일치

  지역명만 바꾼 복제 페이지    금지          검색가치 없는 대량복제
  허구 서비스/성과/경험 생성   금지          FACT FIRST 위반

## 8. 개발 순서

기능 구조는 전체를 확정하되 구현은 **One Axis**로 진행한다.

### 완료

`⑦-F 업체사진` --- `e2d87f8` / CLOSE

1.  공개 사진 연결 --- 검증 완료
2.  사진 기본 상호작용
    -   썸네일 클릭 → 큰 사진 변경
3.  사진 크기·배열
    -   1장
    -   2장
    -   3\~6장
    -   PC
    -   모바일
4.  PRODUCT E2E
5.  최종 diff 확인
6.  commit
7.  ⑦-F CLOSE

### 현재 다음 개발축

미정 (선장 결정 대기).

### 미래 후보 (2F · 현재 구현 승인 아님)

`P-PAGE-SEARCH-DISCOVERY-01` --- P검색확장 2F 미래 후보. 현재 구현 승인 아님.

목표:

``` text
지역 + 하는 일
→ 검색자산
→ 업체 발견
→ 업체 P페이지
→ 직접 전환
```

단, 시작 전 반드시 TRACE한다.

-   현재 지역 FACT SoT
-   현재 서비스 FACT 존재 여부
-   기존 pSEO와 P페이지 역할
-   기존 URL/canonical/robots/sitemap 영향
-   중복 검색의도
-   Blog/pSEO/P페이지 중복 위험
-   신규 DDL 필요 여부
-   검색엔진별 Adapter 경계

TRACE 없이 URL·페이지·DDL을 먼저 만들지 않는다.

## 9. 검색엔진 상단노출 원칙

P페이지 검색기능은 특정 검색엔진을 속이기 위한 임시 SEO 기능이 아니다.

검색엔진이 다음 질문에 명확하게 답할 수 있도록 실제 업체 FACT의 관계를
강화한다.

-   이 업체는 누구인가?
-   어디에 있는가?
-   어떤 지역을 대상으로 하는가?
-   실제로 무엇을 제공하는가?
-   언제 이용 가능한가?
-   어떤 방식으로 일하는가?
-   선택할 실제 이유는 무엇인가?
-   어떻게 직접 연락할 수 있는가?

검색엔진 정책이 변해도 업체 FACT Core는 유지하고 노출 Adapter만 조정할
수 있어야 한다.

## 10. 금지사항

P페이지 개발에서 다음을 금지한다.

1.  실제 업체 FACT가 없는 서비스 생성
2.  AI가 업체 경험·성과·효과·차별점을 임의 생성
3.  지역명만 교체한 대량 페이지 생성
4.  Blog 본문을 P페이지/pSEO에 그대로 복제
5.  검색엔진별 업체 데이터 정본을 별도로 생성
6.  현재 축과 무관한 기능을 동시에 개발
7.  TRACE 없이 DDL·URL 체계·검색구조 변경
8.  기존 FREEZE 엔진을 P페이지 편의를 위해 수정
9.  검색 노출만 보고 실제 전환을 무시
10. AI-POST가 가입업체 대신 상담을 중개하는 구조

## 11. 기능 추가 Gate

앞으로 P페이지에 기능을 추가하기 전 아래 Gate를 통과한다.

``` text
G1. 검색 상단노출에 기여하는가?
G2. 업체를 이해하거나 선택하는 데 기여하는가?
G3. 직접 전환에 기여하는가?
G4. 실제 FACT에 근거하는가?
G5. 기존 SoT/FREEZE/보안/검색구조를 깨지 않는가?
G6. 지금 개발축에 필요한 기능인가?
```

G1\~G3 중 아무것도 만족하지 못하면 원칙적으로 개발하지 않는다.

G4 또는 G5가 FAIL이면 개발하지 않는다.

G6가 FAIL이면 후보 기능으로 보관하고 현재 축에는 넣지 않는다.

## 12. 최종 정의

> **AI-POST P페이지는 지역 사업자의 실제 FACT를 기반으로
> `지역 + 하는 일` 검색에서 노출될 이유를 만들고, 검색자가 업체의 실제
> 사진·서비스·영업정보·업무방식·선택 이유를 확인한 뒤
> 전화·문자·길찾기·문의로 해당 업체에 직접 전환하도록 만드는
> 검색·선택·전환 자산이다.**

### 한 줄 구조

``` text
검색될 이유 → 클릭할 이유 → 확인할 이유 → 선택할 이유 → 연락할 이유
```

### 사업 흐름

``` text
검색 상단노출
→ P페이지 방문
→ 업체 선택
→ 업체 직접 연락
→ 가입업체의 상담·매출 기회
```

## 13. 현재 구현 지시와의 관계

이 문서는 P페이지 전체 방향을 고정하는 Architecture 문서다.

**이 문서 작성 자체가 모든 기능의 즉시 개발 승인을 의미하지 않는다.**

`⑦-F 업체사진`은 `e2d87f8`로 CLOSE되었다. 현재 다음 개발축은 미정이다.\
검색자산·서비스 FACT·FAQ·리뷰 등 후속축은 선장 승인 없이 열지 않는다.

후속 기능은 각각 별도 TRACE → 승인 → 최소 구현 → PRODUCT 검증 → CLOSE
순서로 진행한다.
